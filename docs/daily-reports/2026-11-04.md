## Part C — What we changed and why (for my understanding)

### C1. First full backend build
- **What changed:** commits `680d2d0` (75 files, about 5,000 lines) and `7169f5a` (first database migration). FastAPI app (`backend/app/api/v1/*`), 13 database tables, Celery worker (background job runner), publishing adapters for Facebook, Instagram and LinkedIn, Docker Compose, 27 tests. The migration `0001_initial_schema.py` creates all 13 tables and 9 enum types.
- **What it is for:** everything in the Phase 1 journey: sign in, brand, post, approve, schedule, publish, see the result.
- **Why we did it:** a clean rebuild based on the reviewed architecture documents (Product Roadmap, Product Analysis, Database Architecture, Security Architecture). The commit message says every finding from the earlier reviews is built in "from day one".
- **How it works now:**
  1. The user signs in and gets a short-lived access token. The refresh token (used to get new access tokens) lives only in an HttpOnly cookie, which JavaScript cannot read. It is changed on every refresh and stored hashed.
  2. A post is approved against a **content hash** (a fingerprint of the content). The worker checks the fingerprint again before publishing.
  3. Scheduling: a "Beat" task runs every minute and sends out due jobs (`dispatch_due_jobs`, using `FOR UPDATE SKIP LOCKED` so that two workers never take the same job).
  4. Before calling a platform, the job is saved as "processing" (the commit barrier). If a crash happens, the job is not posted twice.
  5. The second commit stores enum values as lowercase text (`'draft'`) instead of Python names (`'DRAFT'`), so the database CHECK rules match.
- **How we checked it:** 27 unit tests passed. During the review, `alembic check` confirmed that the models and the migration match (from the notes).
- **Explain it in one sentence:** "We built the whole Phase 1 backend in one go, with security and no-double-posting rules built in from the start."

### C3. Approval cannot be bypassed
- **What changed:** commit `e3e7112`. Files: `app/api/v1/posts.py`, `app/core/security.py`, `app/api/v1/media.py`. New endpoint `POST /posts/{id}/withdraw`.
- **What it is for:** acceptance criterion "unapproved content cannot be published".
- **Why we did it:** the review showed that (1) hashtags/CTA could be edited after approval without a new approval, because the fingerprint covered only the caption and media; (2) a post could be changed while it waited for approval, and the approver would approve the new version without knowing.
- **How it works now:**
  1. The fingerprint covers caption + media IDs + hashtags + CTA (and, after C5, the per-platform versions).
  2. While a post is `pending_approval`, edits and media changes return **409** with the message "This post is awaiting approval and is locked. Withdraw it to edit."
  3. `withdraw` moves it back to draft (author or admin only) and writes a history row.
  4. When approving, the server compares the live fingerprint with the fingerprint saved **at submit time** in the approval history. That row is never changed, unlike the `posts.content_hash` column.
  5. Delete and unschedule: only the author or an admin can do it, and never while the post is publishing.
- **Example:** submit → edit hashtags → `PATCH` returns 409. Withdraw → edit → submit again → approve works.
- **How we checked it:** new tests in `tests/test_content_hash.py` (the fingerprint changes when hashtags or the CTA change). The bug was reproduced and then fixed against a throwaway database (from the notes).
- **Explain it in one sentence:** "What the approver reads is exactly what gets published; any change means a new approval."

### C4. Publishing worker fixes and input validation
- **What changed:** commit `e3e7112`. Files: `app/workers/tasks/publish.py`, `app/services/publishing/*.py`, `app/schemas/schemas.py`, `app/core/dependencies.py`, `app/main.py`, `requirements.txt`.
- **What it is for:** posts go out on time, never twice, and errors are visible.
- **Why we did it:**
  - "Publish now" sent arguments the task did not accept, and the error was swallowed (`except: pass`).
  - A hidden bug found while checking the fixes: tasks used `@shared_task`, which attached them to Celery's *default* app. So every dispatch from the API went to RabbitMQ on port 5672, which does not exist in our setup.
  - The `kombu` library had moved to 5.7.0, which does not work with our `redis` client.
  - Bad input caused 500 errors: a long `X-Forwarded-For` header on `/login`, a `null` caption, a 300-character title.
- **How it works now:**
  1. Tasks use `@celery_app.task`, so they go to Redis. Publish-now sends only `job_id`. If sending fails, it is logged, and the Beat scan picks the job up within a minute.
  2. The worker locks the job row. A second copy of the same job either skips (if the first started less than 15 minutes ago) or marks it `needs_review` (if older, because the worker is probably dead).
  3. A timeout on the publish call raises `UnknownOutcomePublishError` → `needs_review`, never retried.
  4. Success is saved *first*. If later bookkeeping (usage log, audit row) fails, it cannot cause a second publish.
  5. Inputs have length limits; an explicit `null` is rejected; database data errors → 422, duplicates → 409. `X-Forwarded-For` (the client IP header) is used only when `TRUST_X_FORWARDED_FOR` is on, and it must be a valid IP.
  6. Uploads must belong to a post (no orphan files) and are capped per post.
  7. Meta: we store `fb_user_id` so the deauthorize/data-deletion webhooks can find the account. Webhooks refuse to run without the app secret.
  8. Library versions pinned: celery 5.5.3, kombu 5.5.4, redis 6.4.0.
- **How we checked it:** +16 tests in total in this commit (`test_validation.py`, `test_worker_guards.py`, client IP, fingerprint coverage). End-to-end with a real Celery worker: publish-now → both mock jobs completed → post marked published (from the notes).
- **Explain it in one sentence:** "Publish-now was silently broken and is now fixed, and if we are not sure whether a post went out, we stop and ask a human instead of posting again."

### C5. Phase 1 backend gaps closed
- **What changed:** commit `f646639`. 5 new endpoints and migration `0002_workspace_self_approval.py`. Files: `posts.py`, `media.py`, `brands.py`, `workspaces.py`, `publishing/base.py`, `seeds/seed.py`.
- **What it is for:** everything the frontend needs for Phase 1 (plan §4).
- **Why we did it:** the plan listed these as missing: adapters ignored `platform_targets`, and the validate, reorder, logo and usage endpoints did not exist.
- **How it works now:**
  - **Per-platform versions:** `platform_targets = {"instagram": {"caption": "..."}}`. A missing field uses the main post's value; an explicit `null` clears it for that platform. The adapters publish the resolved version, and it is part of the fingerprint.
  - **`POST /posts/{id}/validate`:** a dry run (a check that sends nothing). For each account it returns `ok`, `errors`, `warnings`, the rendered text, and the character count and limit. Example warnings: "token expires soon", "LinkedIn publishes text only", "post must be approved first".
  - **`PATCH /media/reorder`:** must list every media item exactly once.
  - **`POST /brands/{id}/logo`:** images only, uses the same upload checks as media, and replaces the old logo.
  - **`GET /workspaces/{id}/usage?days=30`:** counts per operation; `ai_generations` is always 0 in Phase 1.
  - **`GET /workspaces/{id}/posts`:** all posts, with status and brand filters (for the dashboard and the "needs approval" list).
  - **Self-approval:** `workspaces.allow_self_approval`, true for a new one-person workspace. It switches off automatically when the second member is added (`POST /workspaces/{id}/members`, only on the 1 → 2 change, with an audit row and an explanation in the response). Only the owner can change it afterwards. When it is false, author ≠ approver is enforced. Checked on a test database: 11 of 11 checks passed (solo approve works; after the 2nd member the author gets 403 and another admin can approve; owner re-enable survives a 3rd invite).
  - **Seed:** `python -m seeds.seed` creates the demo agency. It refuses to run in production.
- **How we checked it:** +9 tests (`test_adapter_validation.py`, fingerprint covers overrides, `null` override rules). The database guide was regenerated with the new column.
- **Explain it in one sentence:** "The backend now has every endpoint the Phase 1 screens need, including a 'check before you publish' preview."
